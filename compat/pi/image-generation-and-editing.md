## Image Generation And Editing

- When the user explicitly asks for `Fmage 图片退步`, the fixed local 1K/blur/noise recipe, or invokes `/skill:fmage-image-regression`, load `fmage-image-regression` and run its bundled skill script exactly once. This is the default fast path and intentionally bypasses Pi MCP Adapter. Do not also load or call the main `fmage` generation/editing workflow for that request.
- For raster image generation, image editing, color correction, color optimization, retouching, background changes, style transfer, or any other task that produces or edits an image, use the Fmage plugin.
- Load and follow the `fmage` skill (`/skill:fmage`), then call Fmage through Pi MCP Adapter's `mcp` bridge. Use the exact full base tool name exposed by the gateway, such as `Fmage_generate_image`, `Fmage_edit_image`, `Fmage_generate_image_batch`, or `Fmage_edit_image_batch`; provider and prompt-profile routing happens inside those base tools. Do not look for provider-specific image-tool variants, use Codex-style `mcp__Fmage.*` names, or use unprefixed logical names.
- A project workspace is optional. For a successful result, use the three returned path mappings: `display_images[]` for the Markdown preview, `images[]` as the source file path for the saved-image location, and `display_manifests[]` / `display_manifest` (falling back to `manifest`) as the source file path for the generation record. Do not substitute the current session or conversation-storage directory for any returned path.
- When the user has not explicitly named a save folder, omit `output_dir` entirely so Fmage uses `providers.json`. Never pass Pix's project-less conversation-storage path (for example `Documents/Pix/conversations`) as an output override; the MCP server treats that known host directory as session storage and falls back to the configured output directory. A user-requested custom folder remains valid.
- When a project workspace root is available, make the Markdown destinations relative to it. Without a project root, keep Fmage's absolute paths. Use forward slashes and never use `file://`. For Windows absolute destinations, percent-encode the drive colon and reserved characters before putting them in Markdown, for example `D%3A/Downloads/image%20name.png`; Pix decodes this back to the original local path for preview and click handling.
- Report `requested_size` (or `request.size`) together with the actual `image_metadata[].width` and `image_metadata[].height`. Show a short warning only when the dimensions differ or Fmage returns a warning.
- Do not depend on native MCP image content or pass `embed_images: "auto"` as a required compatibility parameter. Treat the returned paths and metadata as authoritative, and do not reopen or process a generated image solely to present it.
- For a completed image response, render every `display_images[]` Markdown preview first, then the compact parameter information, then the location links. Never put the parameter bullets before the preview. If both quality and resolution are displayed, keep them on one line such as `生成质量/分辨率：low / 1k`; if the host cannot keep that pair on one line, omit both display fields rather than splitting them into separate bullets. This display rule does not change the tool arguments.
- The two location links must open the containing folders in Pix's file explorer: derive the target from `dirname(images[])` and `dirname(display_manifests[] / display_manifest / manifest)`, not from the image or manifest file itself. Label them `图片所在位置` and `生成记录所在位置` (or keep the existing `下载 PNG` and `查看 manifest` labels if the surrounding response format requires them), and do not claim that either link downloads or opens the file directly.
- Pix's current Markdown file-link handler opens a path with `workspace.openFile`/Electron `shell.openPath`; a parent-directory link therefore cannot select the child file. Do not replace it with a `file://` URL, shell command, or generated launcher. Selecting the file requires a small Pix host-side `revealInFolder` link action and is outside this compatibility layer.
- When the user explicitly requests any quality tier, including `medium`, always pass that exact `quality`; omit it only when the user did not select a tier. If the selected tier differs from the model default, also pass `quality_user_requested: true`.
- When the user explicitly requests a resolution tier or exact size, pass it with `resolution_user_requested: true`; otherwise omit both `resolution` and `size` so the model default applies. Never infer a resolution override from composition or aspect ratio.
- Never derive image-model `thinking_level` from Pi's session reasoning level. Omit it unless the user explicitly requests it; when requested, pass it with `thinking_level_user_requested: true` and let Fmage validate it against the resolved provider/model.
- After any Fmage image call fails or returns partial results, stop and report the failure. Do not retry, change parameters, query providers to find an alternative, or switch providers unless the user explicitly asks or approves it.
- Treat Fmage `1k`/`2k`/`3k`/`4k` values as resolution tiers. The selected transport's normalized `requested_size` is authoritative; when actual dimensions match it and no size warning is present, do not describe the output as undersized or compare it with `4096x4096`.
