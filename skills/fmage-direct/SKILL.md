# Fmage 直传生图

- Midjourney uses the independent `midjourney` transport. Keep all MJ controls (`--ar`, `--raw`, `--stylize`, `--q`, and unknown flags) in the prompt; never extract or duplicate them as JSON/tool parameters. Existing `--ar` overrides natural-language ratios and inferred poster/canvas shapes. In the expanded entry, do not reinforce a conflicting natural-language ratio; in the direct entry preserve the user's text unchanged. The transport never rewrites prompts. Do not validate prompt flags against the relay's JSON parameter enums.
- For Midjourney, omit structured `aspect`, `size`, `resolution`, `quality`, `background`, `moderation`, `thinking_level`, `response_format`, and output-format/compression overrides. Native output pixels are fixed by the backend; no default 2K/4K or quality-tier mapping applies. Preserve visual-quality words in prompt. Report actual returned dimensions. The generic delivery-parameter extraction/default rules below apply to other model families, not Midjourney.
- The Midjourney transport shares one protocol contract across configured model IDs: the relay accepts one asynchronous submission per call, returns four single images, and takes up to five reference images. Forward the configured `model` unchanged, without a local allowlist, model-specific capability table, or model-dependent routing; the relay selects the upstream. A grid cover is separate, never a single-image slot. Use edit tools for reference generation, without promising pixel-preserving local edits. Select the intended output before continuing with references; never silently select the first or discard excess images. No automatic model fallback or post-generation MJ actions are supported.

- For Banana/Gemini requests, pass the intended aspect ratio or size unchanged. The transport automatically fits unsupported ratios to the nearest supported canvas before the first provider request and adds only the canvas-fit constraint needed to preserve content and geometry. Do not rewrite the prompt yourself for this adaptation, reject the ratio, or ask for approval just to apply it. Report the actual supported output canvas and do not promise a crop back. Actual failed/partial calls still follow the stop rule.

## Entry Selection

- Use this skill only when the user explicitly invokes `/Fmage 直传生图` or `$fmage-direct` for the current image request. Select this entry before any prompt interpretation, attachment inspection, or other image-request processing. Do not load or apply the default `fmage` expansion policy for that request.
- The explicit entry selection applies only to the current image request and its task polling; it is not a persistent setting.
- Set `prompt_mode: "direct"` on the matching image tool call; this records the already-selected entry and does not authorize another prompt-processing pass.

- Reply in Chinese unless asked otherwise; this applies only to user-facing prose, not tool argument content. Keep provider names, model IDs, JSON keys, URLs, env vars, and paths unchanged.
- Use Fmage MCP tools, not scripts. Choose `generate_image` or `edit_image` for one request and the matching batch tool for multiple independent requests. Provider routing is automatic after provider selection; call the selected base tool directly without enumerating or rediscovering tools.
- Fast path for normal image work: first determine whether the request is for generation or editing, then pass the user's prompt text directly to the matching base tool. Only extract delivery settings that the user explicitly stated into the corresponding tool arguments, and remove those same unambiguous setting fragments from the prompt. Simple ordering or grouping is allowed only for extracted delivery-setting fragments; clean only whitespace or punctuation left by that removal. Keep every other character and relative order unchanged. If a parameter boundary is unclear, leave the text unchanged. Do not add, translate, summarize, explain, polish, paraphrase, or otherwise rewrite the prompt. Do not write analysis, a plan, multiple candidates, a separate preparation step, or a status/trace preflight.
- Keep normal Fmage work in the current task. Do not create subagents for prompt writing, translation, comparison, attachment inspection, image submission, or waiting. Put multiple independent image jobs into one Fmage batch call.
- Treat every failed or partial image call as terminal for the current attempt. Stop and report its error or warning. Do not retry the same provider, change parameters and retry, select another provider, or call status/discovery tools to find an alternative provider unless the user explicitly asks for or approves another image call. Do not add a prompt cache lookup, status/trace preflight, or second preparation pass.
- When a user attachment is already clearly visible, pass its supplied path directly to `edit_image`; do not separately open, render, or inspect it first. Inspect only when the requested change depends on image details not visible in the attachment preview.
- After a successful image result, do not call `view_image` or another inspection tool unless the user explicitly requested visual QA or the requested result cannot be verified from the returned metadata.
- Waiting and provider polling are necessary. Let the image tool perform its internal wait. For an asynchronous return, keep exactly one waiter or status check active, use the longest practical wait window, and poll again only after that wait reports the task is still incomplete; never issue concurrent or duplicate status checks.
- Batch `return_when: "completed"` waits up to 40 seconds; `timeout` controls the provider request and cannot extend that foreground window. A returned `status: "submitted"` or `"running"` / `terminal: false` means the batch is already submitted, even when `pending_count` is zero or some images are already available. Stop submitting image requests. Never repeat the batch call, change its timeout and resubmit, or replace it with single-image calls; each creates new billable requests.
- Follow the returned `next_action`: call `get_image_task_status` with the same `task_id` and `wait_seconds: 40`. This waits for the existing local task without generating again. Keep one waiter active and continue only after it returns `terminal: false`; no separate sleep or diagnostic preflight is needed. On a terminal failed/partial/pending result or a status-tool error, report the result and stop. If the status tool is unavailable, report the running task ID and the blocker; never submit a replacement.
- Put the resulting prompt text in `prompt`, with one prompt per batch job. Intent analysis is internal only and must not change the prompt.
- Map an explicit user request for a transparent background, no background, or a cutout to `background: "transparent"`; do not infer transparency from ordinary requests for a white, solid, clean, or minimal background. Keep `output_format: "png"` by default. If the user explicitly requests JPEG together with transparency, pass that explicit format so the image tool rejects the incompatible request before any provider call; do not silently coerce it.
- Preserve all user-provided prompt text except for the exact, unambiguous delivery-setting fragments extracted into tool arguments. Do not introduce labels or additional content.
- Separate delivery parameters from visual language. `quality` controls generation quality/cost/speed, while visual descriptions remain prompt content.
- Treat `output_format` like other delivery overrides: omit it for ordinary image requests so PNG remains the default; pass `output_format_user_requested: true` only when the user explicitly asks for JPEG, WebP, or another non-default format.
- Omit `output_compression` unless the user explicitly requests that compression setting for JPEG/WebP; then pass it with `output_compression_user_requested: true`. A format request alone does not authorize compression, and a compression request does not authorize switching away from PNG. If the compression request conflicts with PNG or lacks a necessary format/value, clarify before submitting. Apply this independently to batch defaults and each job; a different per-job override requires its own explicit user request.
- Interpret `max` from context: an explicit generation-quality request such as `max quality` selects `quality: max` with `quality_user_requested: true`; a model/provider name or another use of `max` keeps its own meaning and routing. Neither a quality tier nor resolution authorizes `output_compression: 100` or a format change.
- Omit `quality` only when the user did not select a quality/speed/cost tier, so the plugin uses the model default `high` for image-series models. When the user explicitly selects any tier, including `medium`, always pass that exact `quality`. If the selected tier differs from the model default, also pass `quality_user_requested: true`. Never infer a tier from resolution alone or infer `high` from professional, final, retouch, color correction, or editing language.
- Explicit `草图质量`, draft quality, preview quality, or low quality selects `quality: low` and `quality_user_requested: true`; for draft/草图 quality also use `resolution: 1k` and `resolution_user_requested: true` unless another resolution was requested. A resolution request alone never selects quality.
- The shared tool enum is not a capability list for every provider. `xhigh` and `max` are native to a confirmed `gpt-image-2.5` series model using `openai-images`; for other models or transports, the server maps an explicit request to `high`, keeps the selected provider and model, and records the mapping in warnings. Do not switch providers or infer `max` from visual-quality wording.
- Pass optional params only when specified or necessary; omit `provider` unless named and `output_dir` unless a save folder is specified. Never choose `resolution` or exact `size` merely from composition, aspect ratio, intended use, model capability, or visual-quality wording. Phrases such as `具备8K超高分辨率`, `8K画质`, `超高清`, `极致清晰`, or `ultra-high-resolution` describe the desired image effect and stay in `prompt`; they do not set a delivery parameter. When the user explicitly selects a delivery resolution tier or exact size, always pass it and set `resolution_user_requested: true`; otherwise omit both so the model default applies. Named providers must be active and may be selected by their full name or a unique `active_providers` shorthand.
- Never derive image-model `thinking_level` from the host session reasoning level. Omit it unless the user explicitly requests it; when requested, pass the value with `thinking_level_user_requested: true`. The server validates it against the resolved provider/model, including after provider shorthand is expanded.
- Treat `1k`, `2k`, `3k`, and `4k` as resolution tiers, not fixed edge lengths. The selected transport resolves the tier and aspect ratio to the actual request dimensions; `requested_size` is authoritative. When saved image dimensions equal `requested_size` and there is no size warning, report normal success. Never compare a tier result with `4096x4096`, call it undersized/nonstandard/provider-capped, or offer a stricter retry unless the user explicitly requested an exact `WIDTHxHEIGHT`.
- When the user states a target ratio (`改成16:9`, `裁成16:9`, or a bare trailing `16:9`), pass it as `aspect` and keep the wording in `prompt`. When the user states pixel dimensions (`1920x1080`), pass them as `size` with `resolution_user_requested: true`; pixels outrank any ratio. When the user states no ratio and supplies no reference image, choose the framing that suits the subject and pass `aspect`, because an unset canvas falls back to `auto` and forfeits the `2k` default. An edit with no stated canvas keeps the reference image's own pixels, normalized to a legal canvas, rather than a tier-sized one. A literal ratio in the prompt is honored even when `aspect` is omitted. `裁成16:9` crops the existing frame, while `改成16:9` produces a wider canvas, so never report one as the other.
- Image-series models default to `quality: high`. `gpt-image-2.5` series models using `openai-images` preserve native `quality: xhigh` and `quality: max`; other models and transports map those explicit tiers to `high` without changing provider or model. Quality is fidelity, not canvas: an explicit `quality` never moves the resolution tier, which is the explicit `resolution` or the `2k` default. Do not infer `4k` from the default `quality: high`; only explicit high-quality wording in the prompt may trigger that semantic upgrade. Visual wording such as `8K超高分辨率` remains in the prompt and does not set a delivery tier. Preserve any explicit user-selected size, resolution, or quality tier.
- Completed output is compact and path-based. Use `display_images` for inline Markdown, for example `![Generated image](C:/Users/name/.codex/fmage/outputs/provider/run/image_1.png)`. No backslashes or `file://`.
- Final responses for completed images: inline images, provider/model, dimensions, saved path(s), and manifest path. Do not add a warning line when there is no blocking error. Mention a size mismatch only when the actual dimensions differ from `requested_size` or the plugin returns a size warning.
- For provider/config questions, setup, dry runs, trace/verbose output, failed/partial requests, or unusual async diagnosis, read [diagnostics.md](references/diagnostics.md) before acting. Normal generation, editing, and ordinary async waiting use the rules above without loading another reference.
