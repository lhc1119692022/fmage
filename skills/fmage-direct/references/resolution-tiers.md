# Resolution Tiers

- Midjourney is excluded from tier/size normalization: keep ratio controls in prompt, never send structured size/resolution/aspect, and report native returned dimensions. No default 2K/4K tier applies.

- `resolution: "1k"`, `"2k"`, `"3k"`, or `"4k"` selects a target resolution tier. It does not promise that either edge will equal the tier number, and `4k` does not mean `4096x4096`.
- Phrases such as `具备8K超高分辨率`, `8K画质`, `超高清`, and `ultra-high-resolution` are prompt-level visual emphasis, not delivery-tier selections. They remain in the prompt unless the user explicitly asks for a supported resolution tier or exact pixel size.
- Fmage combines the tier with `aspect` and the selected transport's limits, then writes the normalized dimensions actually sent upstream to `requested_size` and `request.size`.
- Aspect precedence: explicit `size`, then pixel dimensions written in the prompt, then explicit `aspect`, then a literal ratio written in the prompt (`改成16:9`, `16 : 9`, a bare trailing `16:9`), then the primary reference image for an edit, then framing keywords. A literal ratio is an instruction and outranks the reference image; subject nouns (`car`, `landscape`, `character`) and unrecognized pairs such as a `19:24` timestamp are never read as ratios.
- Pixels outrank ratios: GPT Image accepts a pixel `size`, and a ratio only maps a request onto a canvas. A stated `1920x1080` is requested as pixels (normalized only to the transport's multiple, edge, and pixel limits), never re-derived from a tier; small pairs such as `16x9` stay ratios.
- Generate versus edit: a generate request has no source pixels, so its tier is the explicit `resolution` or the `2k` default, applied at the requested aspect. An edit is anchored to its supplied image, so with no explicit `size`, `aspect`, or `resolution` the reference's own pixels are normalized into a legal canvas (`2095x726` becomes `2096x736`) instead of being re-derived from a tier. An edit that does state a ratio or tier is recomputed from that statement at the reference's aspect, so `1k` on a `2095x726` reference gives `1744x608`.
- `quality` is fidelity, not canvas: `low` still renders at the default tier unless `resolution` is explicit.
- An edit keeps the primary reference image's aspect when no ratio is stated. `裁成16:9` center-crops the reference to that canvas, while `改成16:9` extends it by replicating edge pixels. Transparent padding is avoided because it returns from the provider as black letterbox rows.
- When a generate request names no canvas (no `size`, `aspect`, prompt ratio, or reference image), `requested_size` is `auto` and the provider's returned dimensions stand as delivered. That path is a last resort: the agent is expected to choose the framing, so never describe `auto` as a square or as a 2k result. An explicit tier without an aspect still produces tier-sized square pixels, because `auto` cannot carry a tier.
- Judge delivery against `requested_size`, not the tier label. If `image_metadata` matches `requested_size` and `warnings` contains no size warning, the provider returned exactly what Fmage requested.
- Example: an `openai-images` square `4k` tier can normalize to `2880x2880`; a 16:9 `4k` tier can normalize to `3840x2160`. Both are normal when request and output dimensions match.
- Report a mismatch only when an output's actual dimensions differ from `requested_size`, the plugin emits a size warning, or the user explicitly requested an exact `size` that was not delivered. Do not propose a retry solely to reach `4096x4096`.
