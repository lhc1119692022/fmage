# Diagnostics And Setup

- A failed or partial image call is terminal for the current attempt. Stop and report it. Do not retry the same provider, change parameters and retry, select another provider, or query status/discovery tools to find an alternative provider. Only make another image call after the user explicitly asks for or approves it.
- For ordinary image work, do not add a preparation, optimizer, trace, or status call before the base image tool. The host model performs the required one-pass prompt understanding/expansion in the same turn; then submit that final prompt directly.
- A submitted asynchronous task is not a retry. Use `get_image_task_status` only to follow that same task; never submit a replacement merely because it remains pending.
- An HTTP error while downloading an image URL is a result-delivery failure: it does not prove the image generation failed. The generic async image transport can read the same completed task once with `response_format=b64_json` if its image URL fails; it never resubmits generation for this recovery. If delivery still fails, report the download/query stage and the existing remote task ID. The transport keeps `remote-task.json` in the run's cache directory on failure, without API keys or image URLs; successful delivery moves task metadata into the normal manifest and removes that checkpoint.
- An async submission connection loss before a task ID is received means the remote generation state is unknown. The server can finish the accepted task after the connection closes; a client timeout does not keep a remote connection open. Report `submission_uncertain`, preserve its checkpoint, and stop the attempt. Do not claim generation failed and do not submit a replacement.
- After the user explicitly requests retrieval, use `get_image_task_status` with the owning `provider` and the full `remote_task_id` to retrieve that existing remote task. Omit the local `task_id`. This path only queries `/images/tasks/{task_id}` and saves the returned result; it does not submit generation. A keyless `dry_run=true` validates routing. Never guess a full task ID from a truncated screenshot. If submission lost the ID, obtain it from the provider task log first. Any retrieval failure is terminal for that attempt.
- Use `trace_image_job_plan`, `get_provider_status`, `verbose: true`, `include_provider_metadata: true`, `dry_run`, or `embed_images: "auto"` only when the user requests their specific behavior or diagnosis requires it.
- Prefer `include_provider_metadata: true` when the diagnosis only needs the provider's sanitized response metadata and prompt provenance. It exposes provider IDs, model/usage/status-style fields when returned, while omitting image payloads, URLs, secrets, headers, and repeated prompt copies. Use `verbose: true` only when the full Fmage request, timing, notes, and internal prompt-policy fields are also needed.
- New manifests store prompt history in `prompt_provenance`: `submitted` is always present, `source` is present only when transport adaptation changed it, and `provider_revised` is present only when the provider returned different text. `provider_prompt_status` is `not_returned`, `echoed`, or `rewritten`. Sanitized non-image response fields are stored separately in `provider_response_metadata`. Older manifests using `response_metadata.revised_prompt` remain readable.
- For failed or partial image requests, lead with the error or warning and omit success-only fields that are not actionable.
- Use `get_provider_status` for provider/config questions. Never print API keys.
- If setup is required, relay the config path and required fields in Chinese. Configuration stays outside the plugin at `~/.codex/fmage/providers.json`.
