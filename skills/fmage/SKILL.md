# Fmage

## Prompt expansion and scene clarity

- Perform exactly one concise understanding-and-expansion pass in the current turn. Preserve the user's content, composition, medium, and explicit style; add only useful missing details. Apply the scene requirements below as part of that pass, then call the matching base tool immediately. Keep already-compliant wording nearly unchanged. Do not create a separate optimizer, rewrite pass, plan, or status/trace preflight.
- **Default to connected natural-language prose**, normally one paragraph, with short paragraphs when they improve readability. Weave the scene, subject, lighting, materials, and relevant exclusions into sentences suited to this request. Do not default to field labels, a fixed order of attributes, or a repeated fill-in template. Respect an explicit user format and preserve an already-complete prompt's form. Use a labelled structure only when requested or when needed to disambiguate complex input-image roles, exact text, or edit invariants; a wide or complex scene alone does not require labels.
- **Trigger from the depicted scene, not the provider name.** Apply scene clarity when the request contains a broad environment with foreground/background depth (landscape, terrain, sky, water, streets, architecture, or a large interior), dense or overlapping elements/materials, a complex composite, or an explicit request to remove noise, dirty textures, or ghosting. One main subject in an extensive environment still qualifies: a vehicle on a grassy hill before mountain ranges does not need the words "wide" or "complex" to trigger. Aspect ratio, resolution, quality tier, and "cinematic" alone do not trigger it.
- These are general visual requirements, including for GPT Image. Apply them when only a provider nickname is available or the model family is unknown; do not wait for model identification, infer a family from the nickname, or add a provider/config lookup. The complete core rule is here; reading a reference file is not a prerequisite.
- **For each triggered scene, express the applicable meanings below in the submitted `prompt`. These are content checks, not output headings or a fixed sequence of sentences:**
  - Composition and edges: organize broad, readable shapes and separated depth layers; keep the intended focal subject or focal hierarchy clear, with controlled important boundaries and naturally quieter distant edges.
  - Materials and texture: put material detail where it explains the subject; keep continuous surfaces coherent and simplify distant or supporting texture. Specify where detail belongs instead of asking for sharp microdetail everywhere.
  - Light and contrast: use coherent light/shadow groups, smooth tonal transitions, and selective local contrast while preserving the requested dramatic lighting.
  - Pair those positive goals with concise, explicit exclusions expressed naturally in the same prose. Target relevant unwanted outcomes such as grid-like noise or mottled speckling on continuous surfaces, doubled/ghosted contours or sharpening halos, and repetitive etched/all-over microtexture. Exclude invented visible watermark overlays, pseudo-lettering, or signatures when relevant, without banning required text or logos. No `Avoid:` heading or separate negative-prompt block is required. A lone "no watermark" or "no HDR halos" does not address texture distribution.
- **Do not manufacture texture for realism.** "Photorealistic", "cinematic", high resolution, and `quality: max` do not authorize added film grain, dust/pollen particles, weathering, or excessive grass/rock detail. Do not introduce `ultra-detailed`, `hyper-detailed`, `extremely detailed and sharp`, `ultra-sharp`, Stable Diffusion weights, or generic quality-token piles. Describe the needed material and edge behavior directly. Preserve these effects or explicit words when requested or supported by the chosen reference/medium.
- Preserve intended grain, paper texture, brushwork, dirt, weather, motion blur, real grids/mesh, and balanced multi-focus layouts. Clarity does not authorize plastic smoothing, flattening the medium, deleting scene elements, or changing the user's focal arrangement. For edits, scope these requirements to the requested change and keep the other regions unchanged. Simple assets without scene complexity do not acquire this scene treatment unless cleanup is requested.
- Before submitting, ensure each applicable prompt contains both the positive detail/edge/contrast instructions and corresponding exclusions, with no conflicting texture or sharpening additions. Judge semantic coverage, not labels, field order, or exact stock phrases. Do this while composing the same single-pass result, independently for each existing batch job; a statement in chat or another job's prompt does not carry over. Reuse equivalent user wording rather than duplicating it. This is a host prompt-writing requirement, not an automatic server rewrite or a guarantee about image quality. It applies only to the default expansion entry.

## Tool use and delivery

- Midjourney uses the independent `midjourney` transport. Keep all MJ controls (`--ar`, `--raw`, `--stylize`, `--q`, and unknown flags) in the prompt; never extract or duplicate them as JSON/tool parameters. Existing `--ar` overrides natural-language ratios and inferred poster/canvas shapes. In the expanded entry, do not reinforce a conflicting natural-language ratio; in the direct entry preserve the user's text unchanged. The transport never rewrites prompts. Do not validate prompt flags against the relay's JSON parameter enums.
- For Midjourney, omit structured `aspect`, `size`, `resolution`, `quality`, `background`, `moderation`, `thinking_level`, `response_format`, and output-format/compression overrides. Native output pixels are fixed by the backend; no default 2K/4K or quality-tier mapping applies. Preserve visual-quality words in prompt. Report actual returned dimensions. The generic delivery-parameter extraction/default rules below apply to other model families, not Midjourney.
- Midjourney v8.2 uses one shared protocol contract based on the high-speed API, with the stable documentation as supplementary information. Provider `KC-MJ` defaults to `Midjourney v8.2 高速`; `mj-v8.2` is an alternative server model ID. Forward configured model IDs unchanged, without a local allowlist, model-specific capabilities, or model-dependent routing. The server selects the upstream. The shared contract expects four single images and accepts up to five references. A grid cover is separate, never a single-image slot. Use edit tools for reference generation, without promising pixel-preserving local edits. Select the intended output before continuing with references; never silently select the first or discard excess images. No automatic model fallback or post-generation MJ actions are supported.

- For Banana/Gemini requests, pass the intended aspect ratio or size unchanged. The transport automatically fits unsupported ratios to the nearest supported canvas before the first provider request, preserving content and geometry by extending only the necessary edges. This is normal initial-request adaptation, not a failed-call retry; do not reject the ratio or ask for approval just to apply this rule. Report the actual supported output canvas and do not promise a crop back to the original ratio. Actual failed/partial calls still follow the stop rule below.

- Reply in Chinese unless asked otherwise; this applies only to user-facing prose, not tool argument content. Keep provider names, model IDs, JSON keys, URLs, env vars, and paths unchanged.
- Use Fmage MCP tools, not scripts. Choose `generate_image` or `edit_image` for one request and the matching batch tool for multiple independent requests. Provider routing is automatic after provider selection; call the selected base tool directly without enumerating or rediscovering tools.
- Follow the single-pass expansion requirements above before calling the matching base tool. Output only the final prompt; do not expose analysis or a planning preamble.
- Keep normal Fmage work in the current task. Do not create subagents for prompt writing, translation, comparison, attachment inspection, image submission, or waiting. Put multiple independent image jobs into one Fmage batch call.
- Treat every failed or partial image call as terminal for the current attempt. Stop and report its error or warning. Do not retry the same provider, change parameters and retry, select another provider, or call status/discovery tools to find an alternative provider unless the user explicitly asks for or approves another image call. Do not add a prompt optimizer, prompt-cache lookup, status/trace preflight, or second prompt-rewrite pass.
- When a user attachment is already clearly visible and its role is unambiguous, pass its supplied path directly to `edit_image`; do not separately open, render, or inspect it first. Inspect only when the requested change depends on details not visible in the attachment preview or when the image role/content is ambiguous.
- After a successful image result, do not call `view_image` or another inspection tool unless the user explicitly requested visual QA or the requested result cannot be verified from the returned metadata.
- Waiting and provider polling are necessary. Let the image tool perform its internal wait. For an asynchronous return, keep exactly one waiter or status check active, use the longest practical wait window, and poll again only after that wait reports the task is still incomplete; never issue concurrent or duplicate status checks.
- Batch `return_when: "completed"` waits up to 40 seconds; `timeout` controls the provider request and cannot extend that foreground window. A returned `status: "submitted"` or `"running"` / `terminal: false` means the batch is already submitted, even when `pending_count` is zero or some images are already available. Stop submitting image requests. Never repeat the batch call, change its timeout and resubmit, or replace it with single-image calls; each creates new billable requests.
- Follow the returned `next_action`: call `get_image_task_status` with the same `task_id` and `wait_seconds: 40`. This waits for the existing local task without generating again. Keep one waiter active and continue only after it returns `terminal: false`; no separate sleep or diagnostic preflight is needed. On a terminal failed/partial/pending result or a status-tool error, report the result and stop. If the status tool is unavailable, report the running task ID and the blocker; never submit a replacement.
- Put the result of that one pass in `prompt`, with one complete prompt per batch job. Apply only the constraints relevant to the request; do not perform a separate intent-classification step or expose analysis.
- For every input image, identify it by index and role in the prompt, such as `Image 1: edit target`, `Image 2: style reference`, `composition reference`, `subject reference`, `base scene`, `supporting insert`, or `character anchor`. Do not assume every input is an edit target. When an image is guidance only, state what may be borrowed and what subject, composition, background, or content must not be copied.
- For edits, explicitly state `change only X; keep Y unchanged` and repeat the critical invariants on every iteration. Lock all applicable identity, pose, geometry, proportions, framing, camera angle, untouched regions, edges, layout, typography, text, palette, and style. For compositing, name what moves from which image into which base image and require matched lighting, perspective, scale, shadows, and color temperature.
- Map an explicit user request for a transparent background, no background, or a cutout to `background: "transparent"`; do not infer transparency from ordinary requests for a white, solid, clean, or minimal background. Keep `output_format: "png"` by default. If the user explicitly requests JPEG together with transparency, pass that explicit format so the image tool rejects the incompatible request before any provider call; do not silently coerce it.
- Quote required in-image text verbatim, require no extra characters, and preserve typography, spacing, placement, and hierarchy when the task changes only text. If labelled output is appropriate under the format rule above, choose only labels that clarify this request; do not fill a standard list or invent information to populate fields.
- `Asset type`, `Color palette`, and `Materials/textures` are optional information dimensions, not mandatory output fields. Express useful details directly in the prose. Asset type describes the concrete deliverable and its intended use when that purpose informs layout or finish; it does not authorize an invented commercial use, inferred delivery size, new aspect ratio, or arbitrary left/right placement.
- Palette choices need user-provided colors, relevant reference colors, or material support from the request; omit unsupported choices. Do not invent brand colors or apply a global color cast in place of the requested palette. Material/texture cues describe actual surfaces and their finish, scale, and placement, distinct from the visual medium; include them only when useful and do not add unrequested wear, grain, or all-over microdetail.
- Use [avoid-language.md](references/avoid-language.md) only when additional task-specific phrase pairs or examples are needed during the same expansion pass. Its examples supplement the scene requirements above; skipping this reference does not skip those requirements. Keep desired appearance, unwanted outcomes, edit invariants, and integration requirements clear in meaning; these do not require separate fields or paragraphs.
- Separate delivery parameters from visual language. `quality` controls generation quality/cost/speed; it does not mean sketch, wireframe, placeholder, grayscale, or any other visual style. Keep the requested finished-art direction in the prompt even when `quality` is `low`.
- Treat `output_format` like other delivery overrides: omit it for ordinary image requests so PNG remains the default; pass `output_format_user_requested: true` only when the user explicitly asks for JPEG, WebP, or another non-default format.
- Omit `output_compression` unless the user explicitly requests that compression setting for JPEG/WebP; then pass it with `output_compression_user_requested: true`. A format request alone does not authorize compression, and a compression request does not authorize switching away from PNG. If the compression request conflicts with PNG or lacks a necessary format/value, clarify before submitting. Apply this independently to batch defaults and each job; a different per-job override requires its own explicit user request.
- Interpret `max` from context: an explicit generation-quality request such as `max quality` selects `quality: max` with `quality_user_requested: true`; a model/provider name or another use of `max` keeps its own meaning and routing. Neither a quality tier nor resolution authorizes `output_compression: 100` or a format change.
- Omit `quality` only when the user did not select a quality/speed/cost tier, so the plugin uses the model default `high` for image-series models. When the user explicitly selects any tier, including `medium`, always pass that exact `quality`. If the selected tier differs from the model default, also pass `quality_user_requested: true`. Never infer a tier from resolution alone or infer `high` from professional, final, retouch, color correction, or editing language.
- Explicit `草图质量`, draft quality, preview quality, or low quality selects `quality: low` and `quality_user_requested: true`; for draft/草图 quality also use `resolution: 1k` and `resolution_user_requested: true` unless another resolution was requested. A resolution request alone never selects quality.
- The shared tool enum is not a capability list for every provider. `xhigh` and `max` are native to a confirmed `gpt-image-2.5` series model using `openai-images`; for other models or transports, the server maps an explicit request to `high`, keeps the selected provider and model, and records the mapping in warnings. Do not switch providers or infer `max` from visual-quality wording.
- Treat sketch, hand-drawn, wireframe, and low-fidelity as visual styles only when explicitly requested. Resolve ambiguous `草图` from context without injecting wireframes, gray placeholders, or sketch styling; ask only when the distinction materially changes the result.
- Treat `占位素材`, `临时封面`, and `示意内容` as complete fictional but plausible content in the requested finished style, not empty boxes. Treat `效果图` as a coherent finished composition without decorative annotations or invented copy unless requested.
- Pass optional params only when specified or necessary; omit `provider` unless named. Omit `output_dir` unless the user explicitly specifies a save folder; never infer it from the current workspace, input image path, or conversation context. When the user specifies a save folder, pass `output_dir` with `output_dir_user_requested: true`. Otherwise omit both so the configured output directory applies. Never choose `resolution` or exact `size` merely from composition, aspect ratio, intended use, model capability, or visual-quality wording. Phrases such as `具备8K超高分辨率`, `8K画质`, `超高清`, `极致清晰`, or `ultra-high-resolution` describe the desired image effect and stay in `prompt`; they do not set a delivery parameter. When the user explicitly selects a delivery resolution tier or exact size, always pass it and set `resolution_user_requested: true`; otherwise omit both so the model default applies. Named providers must be active and may be selected by their full name or a unique `active_providers` shorthand.
- Never derive image-model `thinking_level` from the host session reasoning level. Omit it unless the user explicitly requests it; when requested, pass the value with `thinking_level_user_requested: true`. The server validates it against the resolved provider/model, including after provider shorthand is expanded.
- Treat `1k`, `2k`, `3k`, and `4k` as resolution tiers, not fixed edge lengths. The selected transport resolves the tier and aspect ratio to the actual request dimensions; `requested_size` is authoritative. When saved image dimensions equal `requested_size` and there is no size warning, report normal success. Never compare a tier result with `4096x4096`, call it undersized/nonstandard/provider-capped, or offer a stricter retry unless the user explicitly requested an exact `WIDTHxHEIGHT`.
- Image-series models default to `quality: high`. `gpt-image-2.5` series models using `openai-images` preserve native `quality: xhigh` and `quality: max`; other models and transports map those explicit tiers to `high` without changing provider or model. When no explicit resolution semantic is established, non-Midjourney models default to the `2k` resolution tier. Do not infer `4k` from the default `quality: high`; only explicit high-quality wording in the prompt may trigger that semantic upgrade. Visual wording such as `8K超高分辨率` remains in the prompt and does not set a delivery tier. Preserve any explicit user-selected size, resolution, or quality tier.
- Completed output is compact and path-based. Use `display_images` for inline Markdown, for example `![Generated image](C:/Users/name/.codex/fmage/outputs/provider/run/image_1.png)`. No backslashes or `file://`.
- Final responses for completed images: prompt summary, provider/model, saved path(s), dimensions, manifest path, and inline images. Do not add a warning line when there is no blocking error. Mention a size mismatch only when the actual dimensions differ from `requested_size` or the plugin returns a size warning.
- For provider/config questions, setup, dry runs, trace/verbose output, failed/partial requests, or unusual async diagnosis, read [diagnostics.md](references/diagnostics.md) before acting. Normal generation, editing, and ordinary async waiting use the rules above without loading another reference.
